# Testing

Preheat uses unit tests, a software-rendered game lab and a harness for real graphics cards. CI runs deterministic checks only.

| Layer | Location | Coverage |
| --- | --- | --- |
| Unit and script tests | `./gradlew build`, `scripts/tests/` | Logic outside the game, compatibility checks against pinned jars, neighbouring mixin targets, and every Python script |
| CPU-only lab | `scripts/lab/` | Loading and settings screens, portal trips, cache behaviour and NeoForge under Mesa llvmpipe |
| Real-game harness | `scripts/realgame/` | A copied instance on a physical GPU, cold and warm cache checks, startup and portal measurements |

Downloaded runtimes and game results belong in the gitignored `run/` folder. The test driver is the Gradle subproject `testmod/`; it is never shipped.

## Unit and script tests

```sh
python3 scripts/fetch-deps.py
./gradlew build
make test-scripts
```

The Gradle build checks formatting, runs Error Prone and NullAway, and executes the tests, including the compatibility matrix. JaCoCo requires 100% of lines and branches in the counted classes.

Only thin adapters that need a running game are excluded. These include mixins, loader entry points, screens and OpenGL or Iris adapters. Each exclusion has a reason in `build.gradle.kts`. New decisions belong in counted classes.

| Report               | Path                                        |
| -------------------- | ------------------------------------------- |
| Java tests           | `build/reports/tests/test/index.html`       |
| JaCoCo               | `build/reports/jacoco/test/html/index.html` |
| Compatibility matrix | `build/reports/compat/matrix.md`            |

`make test-scripts` holds every Python script under `scripts/` to 100% line and branch coverage with `coverage` 7.6.10, the lab and real-game ones included: they read logs and recordings that the tests write by hand, so no game is needed. The shell scripts in `scripts/lab/` and `scripts/realgame/` start games and are checked by shellcheck only.

## The CPU-only lab

`scripts/lab/setup.sh` prepares a client from a Modrinth App instance and a fixed-seed world generated by the vanilla server. It copies the instance's files without modifying the source instance. The lab renders through Mesa llvmpipe on Xvfb under Linux or WSL.

The setup script currently expects the launcher's Minecraft 26.3 Fabric installation and `ComplementaryReimagined_r5.9.3.zip`. Its pinned runtime selection is recorded in the script.

The lab game's Java heap starts at 1 GB. `LAB_HEAP` sets its maximum and defaults to `3G`, so the lab can run beside other work on an ordinary machine. The vanilla server that `setup.sh` runs once to make the test world uses 2 GB.

Run from the repository root, replacing the example paths:

```sh
MODRINTH_META="/path/to/ModrinthApp/meta" MODRINTH_INSTANCE="/path/to/ModrinthApp/profiles/instance" scripts/lab/setup.sh
./gradlew build :testmod:build

scripts/lab/loading-screen.sh first-launch
COLD_CACHE=1 scripts/lab/loading-screen.sh cold
OPEN_SETTINGS=true HOLD=20 scripts/lab/loading-screen.sh screen
OPEN_SETTINGS=video HOLD=20 scripts/lab/loading-screen.sh page

scripts/lab/run.sh trips fixed
scripts/lab/run.sh trips-stock stock
scripts/lab/ore-scene.sh ores fixed
scripts/lab/neoforge.sh neoforge
```

To raise the lab game's heap limit to 4 GB for a trip run:

```sh
LAB_HEAP=4G scripts/lab/run.sh trips fixed
```

The loading-screen script captures 4 screenshots a second. The settings examples hold the relevant screen for 20 s. `ore-scene.sh` creates a dark room of ores for checking emissive rendering. `neoforge.sh` installs its runtime into `run/lab/neoforge/` and checks Minecraft 26.3 on NeoForge.

Runtime downloads and prepared instances are under `run/lab/`. Each labelled run keeps logs and screenshots in `run/lab/results/<label>/`; route results are also collected in `run/lab/results/results.csv`.

Read the `PREHEAT` lines and inspect the screenshots before treating a visual change as verified. Software-rendering timings identify expensive work but do not predict a physical GPU's frame times.

### Test driver and recordings

Build the driver with:

```sh
./gradlew :testmod:build
```

Its Java system properties use the `testmod.*` prefix, for example `-Dtestmod.openSettings=true`. The scripts set these properties for their routes and screen checks.

`scripts/lab/run.sh` accepts `JFR_STEPS` to select route steps for profiling. `scripts/lab/jfr-split.py` analyses the render-thread samples in those recordings.

## The real-game harness

`scripts/realgame/run.sh` copies an instance into a work folder and adds the selected Preheat build and test driver. It launches the copy on the machine's graphics card twice:

1. A cold Preheat-cache run opens a test world, travels Overworld, Nether, Overworld, End, Overworld, disconnects and quits.
2. A warm run repeats the route using the saved shaders from the first run.

Here, cold and warm refer to Preheat's cache. The graphics driver's cache is unchanged by this harness.

`scripts/realgame/check.py` reads both logs. It checks for startup diagnostics, disabled features, Preheat errors, driver refusals, warm-cache misses after accounting for unsaveable programs, unexpected warm-run builds during trips, slow reuse and a completed disconnect trace.

The report includes GPU and driver information, build times and cache hits, dimension changes, longest frames, available video memory where reported, and disconnect work. It ends with `PASS` or `FAIL`. Results are stored in `run/realgame/<time>/`.

The harness refuses to start while Minecraft is running and stops at the first failed launch. It does not retry. Before each launch it sets `soundCategory_master:0.0` in the work copy's `options.txt`; the source instance remains unchanged.

### Prerequisites

- A Minecraft 26.3 Fabric instance with Iris, Sodium and a shader pack.
- Launcher metadata arranged as `versions/`, `libraries/` and `assets/`, as in the Modrinth App.
- A Java 25 runtime and a desktop session with a graphics card.
- A test world from `scripts/lab/setup.sh`, or another world selected through `TEST_WORLD`.
- A successful `./gradlew build :testmod:build`.

### Running it

Replace the example paths:

```sh
SOURCE_INSTANCE="/path/to/instance" \
WORK_DIR="/path/to/empty-work-folder" \
MC_META="/path/to/launcher/meta" \
JAVA="/path/to/java-25/bin/java" \
MEMORY_MB=8192 scripts/realgame/run.sh
```

For a Windows installation launched from WSL, use Windows Java, such as `javaw.exe`, and place `WORK_DIR` under `/mnt/c`. The launcher converts paths.

`TRIPS` changes the route. A `reload` entry reloads resources, like F3+T or a server resource-pack reload. `PREHEAT_JAR` selects another build for comparison.

`scripts/realgame/copy-instance.sh` handles the work copy. `scripts/realgame/launch.sh` can also launch a game to the title screen using `GAME_DIR` instead of `SOURCE_INSTANCE`, together with `MC_META`, `JAVA` and the memory setting. These launches are offline and cannot join an authenticated online server.

Run the harness only when the machine is available for testing. Stop after a game crash, driver error or lost GPU.

## The startup and portal benchmark

`scripts/realgame/bench.sh` uses the same instance and runtime variables. It interleaves launches without Preheat, with an empty Preheat cache and with a filled Preheat cache. `ROUNDS` defaults to 3 per condition.

The default benchmark also separates cold and warm driver-cache conditions, giving these names:

| Condition     | Preheat      | Driver cache   |
| ------------- | ------------ | -------------- |
| `stock-dcold` | Absent       | Cold           |
| `cold-dcold`  | Empty cache  | Cold           |
| `warm-dcold`  | Filled cache | Cold           |
| `stock-dwarm` | Absent       | Existing cache |
| `cold-dwarm`  | Empty cache  | Existing cache |
| `warm-dwarm`  | Filled cache | Existing cache |

The cold-driver method is specific to the tested NVIDIA Windows setup. Each launch uses a copy of the Java runtime with a fresh executable name. The script records newly created driver-cache files in `driver-cache-created.txt` and removes those files and the copied runtime afterwards. It stops if no new driver-cache entry is observed.

Do not redirect NVIDIA's driver cache through the game's environment. That approach crashed the driver during testing. On other setups, select the warm-driver conditions with `CONDITIONS=stock-dwarm,cold-dwarm,warm-dwarm` unless a cold-cache method has been verified.

By default, each launch reaches the title screen and then follows the portal route. Set `TRIPS=""` for startup-only measurements.

`scripts/realgame/bench.py` reports medians and ranges for title-screen time, startup build components and portal frames. Results include per-launch logs, `bench.csv` and `summary.txt` under `run/realgame/bench-<time>/`. Published results are in [performance](performance.md).

### Judging a result

Preheat moves cost from the portal trips to the title screen, so a slower title screen is not a failure on its own. A change passes when, for both a cold and a warm driver cache, the title-screen time Preheat adds is no more than the time it saves on the first Nether and End trips together, compared with the same driver cache without Preheat. Report both sides and the net, the way [performance](performance.md#the-net-comparison) does. A trip that differs by less than 50 ms is within one run's noise; run it again with `ROUNDS=3` before drawing a conclusion.
